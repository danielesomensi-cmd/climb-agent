- **[2026-03-31] [B169]**: `user_state.equipment.gyms` usa `gym_id` UUID (assegnato da `_ensure_gym_ids` in onboarding), ma il frontend caricava i gym con cast `{ name, equipment }` perdendo il campo — il dialog passava il nome come gym_id, il resolver non trovava match e usava il fallback (primo gym per priorità). Quando si propagano identificatori tra frontend e backend, verificare sempre che il campo chiave usato dal resolver (`gym_id`) sia incluso nel tipo TypeScript e nel cast dello state.
- **[2026-03-31] [debug produzione]**: Per leggere lo stato di un utente in produzione NON usare `X-Clerk-User-Id` — il backend non accetta quell'header per `/api/state`. Il flusso corretto è: (1) `GET /api/admin/users` con `X-Admin-Key` per listare tutti gli UUID interni con nome/grade, (2) identificare l'UUID corretto, (3) `GET /api/state` con header `X-User-Id: <uuid>` + `X-Admin-Key`. Senza `X-Admin-Key` il backend usa solo Clerk JWT e non è invocabile da curl.
- **[2026-03-31] [B178]**: Gli script diagnostici non devono mai hardcodare path di file catalog/data. Includere sempre uno step di discovery (`find`) prima di qualsiasi script path-dependent. Path hardcodati hanno causato falsi risultati MISSING nell'audit del campo `unilateral`. Si applica a tutte le fasi D-type e B-type.
- **[2026-03-31] [B179]**: Negli script diagnostici su user_state, verificare sempre il key path esatto dalla struttura reale (es. `state["working_loads"]`, NON `state["baselines"]["working_loads"]`). Path annidati sbagliati restituiscono silenziosamente valori vuoti/mancanti e causano falsi allarmi P1. Aggiungere `print(list(state.keys()))` in cima a ogni diagnostica per confermare la struttura prima di scendere nei campi.
- **[2026-03-31] [B174]**: Bug items fixati in un brief ma non marcati Done in ROADMAP_CURRENT.md causano tempo perso a re-investigare lavoro già chiuso. Regola: ogni brief che chiude un item del roadmap DEVE includere uno step che lo marca Done prima della fine della sessione.

- **[2026-04-23] [B221]**: Parity audits must check the full resolver's emitted-field set against the UI's read-field set, not the audit's find list. D220 initially under-reported the gap because it focused on description/cues only — 4 additional fields (`video_url`, `unilateral`, `alt_sides`, `attributes`) were emitted by the full resolver and read by the guided UI but never surfaced in the audit's delta table. - **[2026-04-23] [B224]**: Body-part picker's three-tier role cascade (main → main+accessory → all roles) must be filled tier-by-tier and concatenated, not by pooling eligible roles into one flat list and score-sorting. A flat-pool approach breaks main-preference because `score_exercise()` doesn't penalize accessory/warmup vs main — recency + prefs tie, jitter decides, and main sometimes loses to accessory in tier 2. Tier-first-then-score preserves role ordering while keeping deterministic ranking among peers.
- **[2026-05-04] [B247]**: Wall-clock timer derivation (`Math.ceil(remainingMs/1000)`) + `useEffect([secondsLeft])` gate + 1s `setInterval` is a fragile combination on iOS PWA: any tick drift can land outside the 1-s window and silently drop the beep. Counter-decrement was robust to drift but fragile to backgrounding (the original B67 trade-off). Correct pattern (already in 4 other timers in repo): sub-second tick (200 ms), in-tick check with `lastBeepedSecRef` dedup, reset on every phase transition. Open-threshold transitions (`remainingMs <= 0`) are robust; window-based gates need fine ticks + dedup.
- **[2026-05-05] [B248]**: Manually transcribed conversion tables drift from authoritative sources. The Font→V map in `gradeUtils.ts` was inflated by +1 across 5A..7A vs Wikipedia/Mountain Project standard, undetected for ~4 weeks because tests covered only 7A (which happened to be wrong) and a few other random points. Lesson: any conversion-table data should ship with a parametric test that pins **every** entry against the authoritative source on day one, not just spot-check a handful of values.

- **[2026-05-06] [B-NEWMACRO-DEADLINE-FIX]**: `request()` in `frontend/src/lib/api.ts` formatta gli errori come `Error("API ${status}: ${body}")` — il body grezzo finisce nel `.message`. Renderlo direttamente in UI (`<p>{error}</p>`) leak technical detail. - **[2026-05-07] [B-NEWMACRO-STARTDATE-FIX]**: Decisione di design "evita overlap timeline" (`max(current.end_date+1, today)`) può sembrare conservativa ma in realtà rompe la UX quando l'utente ha un cycle ongoing lungo: clic "Start New Cycle" mid-cycle → date di inizio mesi avanti, utente senza piano in interim. Ogni volta che un dialog UI già comunica "discard / archive", la logica backend NON deve aggiungere wait semantics — l'archive **è** la continuity. Pattern: se la UI dice "ora", il backend deve fare "ora". Helper `strict_next_monday(today)` esisteva già in `start_date_utils.py:43` con la semantica giusta — bastava chiamarlo invece di reinventare `_next_monday_on_or_after` con `max(end+1, today)`.
- **[2026-05-07] [A218]**: Algoritmi di allocazione "default + flex absorber" senza cap superiori convergono su distribuzioni innaturali quando `total_weeks` cresce: lead a 21w produceva 12/4/2/2/1 con base inflated. Pattern corretto: per ogni risorsa allocabile, definire **floor**, **cap**, e una **priority list** per il riempimento del surplus. Il flex absorber prende quello che resta; non può mai superare il proprio cap. Simmetria per shortfall: reduce in inverse priority, never below floor. Senza questa struttura, l'algoritmo è "pseudo-determinista" — output formalmente coerente (sum corretto) ma semanticamente sbagliato.
- **[2026-05-07] [A218]**: Quando un'algoritmica esistente ha due funzioni quasi-duplicate (full vs incremental regen), preferire **una sola funzione con scope parametrizzato** (`phases=...`) rispetto a "due funzioni che condividono helper". I duplicati derivano sempre da costanti hardcoded ribattute (`_compute_remaining_durations` aveva `> 2` invece di `> shrink_floor`) — drift inevitabile. La consolidazione è più sicura del DRY tramite extract-helper, perché elimina il punto di drift invece di nasconderlo.
- **[2026-05-07] [A218]**: Tabelle di verifica scritte a mano nel design doc sono fonti di drift. Lezione: la suite di test è la ground truth, non la tabella; quando si specifica un algoritmo deterministico in un design doc, generare le tabelle dall'algoritmo (anche solo Python a mano) prima di fidarsi delle proprie sottrazioni.

- **[2026-06-10] [B258/D243]**: Un paywall fail-closed deve distinguere gli stati "mai iniziato" (`none`, `pending_checkout`) da "trial finito" (`past_due`/`canceled`/`expired`) sia nel **messaggio backend** sia nel **banner frontend** — altrimenti chi non ha mai completato il checkout vede "Your trial has ended" (mai avuto un trial) e, se il banner è soppresso per quello stato, resta in un vicolo cieco senza CTA mentre ogni azione 402a. Inoltre: `check_subscription` tratta `trialing` come attivo senza ricontrollare `trial_end`, quindi un webhook Stripe mancato lascia l'utente in accesso gratuito indefinito → serve riconciliazione (proposta in roadmap).
- **[2026-06-14] [D245]**: `BYPASS_USER_IDS` ≠ esenzione pagamento. Il bypass apre solo il guard di accesso (B202), **non** tocca il billing Stripe: un friend&family aggiunto al bypass ma passato dal checkout riceve comunque il trial standard e viene addebitato alla scadenza. Per dare un periodo gratuito davvero: o non far inserire la carta, o applicare un coupon 100%-off al checkout/subscription. Corollario diagnostico: per capire se i webhook Stripe arrivano al backend, controllare `pending_webhooks` sugli `stripe.Event` — un valore >0 su eventi vecchi giorni = delivery mai confermata (2xx) → pipeline rotta (qui: probabile mismatch `STRIPE_WEBHOOK_SECRET`). La riga DB ferma a `pending_checkout` mentre Stripe ha la sub `active`+pagata è la firma di questo guasto.
- **[2026-06-17] [B259]**: `stripe.Webhook.construct_event()` ritorna uno `stripe.Event` (StripeObject), e stripe-python ≥8 ha rimosso `dict.get()` da StripeObject → `event.get("id")` solleva `AttributeError`. Per il codice di parsing webhook usa **bracket access** o converti subito a dict (`to_dict_recursive()`); non usare `.get()` su oggetti Stripe grezzi (event/customer/subscription/invoice). I test mockavano l'evento come `dict` (che ha `.get`) → passavano mentre prod faceva 500 su ogni delivery: un regression test per gli handler Stripe deve mockare `construct_event` con un **vero StripeObject** (`stripe.Event.construct_from(...)`), non un dict. La regressione è arrivata da un **bump silenzioso**: tutte le dipendenze in `backend/requirements.txt` erano unpinned → pinnare almeno le librerie su path critici (billing). Diagnosi via `railway logs` (la riga del traceback indica l'esatto file:line) + POST firmato col secret di Railway per isolare "firma" da "handler".
- **[2026-06-17] [B259]**: Rifare (resend) un webhook Stripe **non genera mai un addebito** né tocca coupon/sconti — è solo il replay di una notifica. Ma NON è sempre idempotente lato nostro: `_handle_checkout_completed` forza `status="trialing"` con le date trial originali, quindi ri-inviare un vecchio `checkout.session.completed` a un utente ora `active` lo **declasserebbe**. Per allineare una riga già corretta non rifare gli eventi: o riconcilia direttamente il DB (Stripe è source-of-truth) o rifai solo l'evento che porta allo stato giusto.
- **[2026-06-19] [C241/OPS]**: The session-start git snapshot is a point-in-time capture and can be stale — it reported `feat/A223-plan-pause` while the live checked-out branch was `brief/A224-weather-today`, so C241 commits landed (and were pushed) on the wrong branch. Wrong-branch commits on a branch under preview review create divergence and future merge friction. Rule: run `git branch --show-current` immediately before ANY commit/push — never trust the session-start snapshot. Keep the convention: backend-only work → push to `main`; only frontend work uses a `brief/` branch.
- **[2026-06-19] [B260]**: A hardcoded `ex_id != "..."` exclusion in a data-driven path turns the catalog config into **dead code**. `limit_bouldering` carried correct `grade_ref: boulder_max_rp` / `grade_offset: 0` in the catalog, but `inject_targets` excluded it from the catalog grade path and re-derived the target from a parallel board-benchmark source — so the (correct) catalog values were never read and the target silently diverged (7A vs 7C). When auditing a "wrong value" bug, don't stop at the config: verify the config is actually *consumed*. A grep for `ex_id ==`/`ex_id !=` near the derivation reveals special-case bypasses fast.
- **[2026-06-19] [A225/D1]**: The "filter by equipment, not location" rule applies to **session/exercise filtering**, not to **venue detection**. An outdoor day is legitimately detected via `availability.*.location == "outdoor"` because "outdoor" is a venue with no indoor-equipment profile to gate on — the planner reads the flag only to *exclude* the day from indoor assignment (`day_is_outdoor`), never to filter a trainable session. Documented as a standing exception in `vocabulary_v1.md §1.1`; needed no `planner_v2` change. When a new feature seems to "violate" the equipment-vs-location principle, first check whether it's filtering a session (rule applies) or detecting a context (exception).
- **[2026-06-19] [A225]**: Catalog vocabularies must match the **engine** vocabulary, not the KB/source doc's. C241 authored the outdoor strategy catalog's `macrocycle_phase` patches with KB names (`build`, `peak`) while the engine emits `strength_power`, `power_endurance` — forcing a translation layer in the resolver. Fixed by renaming the catalog keys to the engine vocabulary so lookup is direct (one vocabulary, no mapping). When a new catalog keys off an existing engine enum, copy the enum's exact values from the engine, not from the brief/KB prose.
- **[2026-06-19] [B261]**: When an explicit `exercise_id` pin is made to fall back to filter-based selection (P0) on equipment-incompatibility, that fallback is **dangerous for test/measurement blocks**: P0 by `role=test` will happily substitute a *different* test (a hangboard max-hang pin → `test_hip_flexibility`), silently measuring the wrong axis. A pinned measurement is semantically "this exact exercise or nothing" — on incompatibility it must **skip**, never substitute. Guard via `role contains "test"`. General rule: a generic fallback that's correct for substitutable blocks (warmups, accessories) can corrupt non-substitutable ones (tests) — classify the block before delegating.
- **[2026-06-19] [B261]**: `compatible_with_location()` in `resolve_session.py` reads `ex.get("equipment")` (a near-unused field) and ignores BOTH `equipment_required` and `equipment_required_any` — so it would NOT have caught the `warmup_easy_boulders` leak (which gates via `equipment_required_any`). The real equipment gate lives inline in `pick_best_exercise_p0` Stage 2. Before reusing a plausibly-named predicate, confirm it reads the field your case actually uses — name ≠ behavior.
- **[2026-06-20] [B266]**: A Safari/iOS "Load failed" (a `fetch()` TypeError, not an HTTP status) on a write usually means the request got **no CORS-valid response** — most often a backend **500 whose error response lacks CORS headers**, so the browser masks the real status. Don't trust the client string: capture the server traceback. Here the 500 was `postgrest APIError 23505` — a Supabase `.upsert()` **without `on_conflict`** defaults to the serial PK as conflict target, degrading to an INSERT that violates a `(user_id, X)` unique constraint on the second write. Always pass `on_conflict="<unique cols>"` when the table's uniqueness is NOT its PK. Repro tip: the bug only appears on Supabase with a **pre-existing row** for that key — file backend and fresh test users both pass; reproduce against the real account (or seed the conflicting row).
- **[2026-06-21] [A223]**: For a date-shift feature (plan pause/resume), shifting the immutable anchor (`start_date`) is the *wrong* lever even when it looks cleaner: completed past weeks fall below the new anchor and get **expelled** from the `[start_date, end_date]` completion window (`macrocycle_archive`). Option B — keep `start_date` immutable, add a cumulative offset read ONLY by the forward-position consumers (the 2 in `deps.py`), extend `end_date` — preserves past accounting by construction. Measure the offset **Monday-to-Monday** (always ×7) so the Monday-invariant holds for free; the intra-week partial is already handled by the planner's `today` param.
- **[2026-06-21] [A223]**: "Paused" vs "missed" is a **display-only, read-time derivation** from the pause log — never mutate a session record to mark it paused (that would break past-session immutability). Same principle as B3 in A227: classify at render, don't rewrite history. Recency/closed-loop easing after a layoff is *correct* behavior and was deliberately left untouched.
- **[2026-06-21] [A223]**: A long-lived feature branch can fall far behind `main` (here 54 commits / a new `weather` router landed meanwhile). `git rebase main` cleanly auto-merged non-overlapping router registrations — but always re-run the FULL suite after the rebase, and isolate any new red by re-running it at the branch-point commit *today*: a date-dependent failure (Sunday) that reproduces at the old commit with identical code is pre-existing, not your regression.
- **[2026-06-26] [B267]**: Silent variety-death from future-week saturation: `load_recent_exercise_ids` took the N **newest** `week_plans` keys by date, but the hot store also holds PRE-GENERATED FUTURE weeks (`status != done`). With ≥N future weeks pre-generated, the recency window filled entirely with future placeholders → `recent_ex_ids = []` → every selection block fell to the alphabetical tie-break (anti_rotation → always `copenhagen_plank`, never `pallof_press`). The user saw "same exercises every time, never X". Fix: filter `key > current_week_monday` (a `reference_date`, default today) BEFORE the top-N slice AND before the "<N hot → consult archive" decision (so that decision counts PAST weeks only). General rule: a "most-recent-N-keys" window over a store that contains BOTH past and future entries is a latent bug — bound it by `<= now`, and verify the empty-recency path isn't masking dead variety (an empty recency list looks innocuous but disables all rotation).
